# Reseed Pipeline Design — Discussion

## Problem

Client holdings contain products whose `product_id` does not match the
`STOCK-{TICKER}` / `ETF-{TICKER}` convention used by `product_catalog_seed.py`.
The PFS engine joins `holdings.product_id → products.product_id` and silently
skips holdings with no match, producing incorrect experience and
better-product scores.

Example: Emma Thompson holds `1810-hk` (Xiaomi). The seeder creates
`STOCK-1810.HK` but never `1810-hk`.  Both refer to the same instrument.

## Design Principles

1. **`risk_rating` and `expected_return` must not be hardcoded.**
   They are auto-computed by `get_market_data` from Yahoo historical data
   using configurable rating tables in `config_marketdata.yaml`.

2. **Tickers should be grouped and named**, not scattered across config files.
   A ticker group already exists (`demo-market-1Jun26`). A new concept
   `duckdb_ticker_groups` would define which tickers need manual product_id
   bridge rows.

3. **The reseed pipeline should be a single command**:
   `python -m src.test_data.reseed`

### Per-entry fields

| Field | Required | Source |
|---|---|---|
| `product_id` | ✅ | Holdings table (exact match) |
| `ticker` | ✅ | Yahoo Finance symbol |
| `name` | Optional | Falls back to Yahoo `longName` if omitted |
| `sector` | Optional | Falls back to `asset_class` from holdings |
| `product_type` (group-level) | ✅ | `stock`, `bond`, `money_market_fund`, `currency` |

### Fields derived from market data (NOT in config)

| Field | Source |
|---|---|
| `risk_rating` | `get_market_data` → CSV `risk_rating` column |
| `expected_return` | `get_market_data` → CSV `expected_return` column |
| `performance_history` | `get_market_data` → CSV return/risk columns |
| `investment_note` | Auto-generated by `_generate_investment_note` |

## Proposed Pipeline Flow

```
python -m src.test_data.reseed
  │
  ├─ 1. get_market_data_from_config(config_path)
  │     Merges ticker_groups + duckdb_ticker_groups tickers
  │     → data/planbot/shared/product_catalog/selected_etf.csv
  │     (CSV now includes 1810.HK, BRK-A, 2018.HK, US5YT=RR, …)
  │
  ├─ 2. product_catalog_seed.seed()
  │     Reads CSV → creates STOCK-{ticker}, ETF-{ticker} rows
  │     (standard flow, no changes needed)
  │
  └─ 3. Bridge: duckdb_ticker_groups → INSERT
        For each entry:
          a. Look up risk_rating, expected_return, performance_history
             from the CSV row matching `ticker`.
          b. INSERT INTO products with `product_id` = the holdings-compatible ID
          c. Copy type_specific from the canonical STOCK-{ticker} row
             if it exists, or synthesize minimal version.
```

### Step 3 logic (pseudocode)

```python
def _insert_bridge_rows(conn, csv_path, ticker_groups):
    csv_data = {row["ticker"]: row for row in read_csv(csv_path)}
    
    for group_name, group in ticker_groups.items():
        product_type = group.get("product_type", "stock")
        for entry in group["entries"]:
            pid = entry["product_id"]
            ticker = entry["ticker"]
            csv_row = csv_data.get(ticker)
            
            if csv_row is None:
                print(f"  ⚠ {pid}: ticker {ticker} not in CSV — skipping")
                continue
            
            row = {
                "product_id": pid,
                "name": entry.get("name") or csv_row.get("name", pid),
                "ticker": ticker,
                "risk_rating": csv_row["risk_rating"],       # ← from Yahoo
                "expected_return": csv_row["expected_return"], # ← from Yahoo
                "region": _infer_region(ticker, csv_row["asset_class"]),
                "sector": entry.get("sector", csv_row["asset_class"]),
                "product_type": product_type,
                "performance_history": extract_perf(csv_row),
                # …
            }
            conn.execute("INSERT OR REPLACE …", [row[k] for k in DDL_COLUMNS])
            print(f"  ✓ {pid:20s}  risk={row['risk_rating']}  er={row['expected_return']}")
```

## Open Questions

1. **Should `duckdb_ticker_groups` live in `config_marketdata.yaml` or a new file?**
   - Pro: same file = single source of truth for all tickers
   - Con: mixes market-data concerns (Yahoo fetch) with DB-seed concerns

2. **`product_type` for treasury yields** — `bond` or `bond_fund`?
   Holdings classify them as `Fixed Income`. The seeder classifies treasury ETFs as `bond_fund`. For individual yields (`US5YT=RR`), `bond` may be more accurate.

3. **Should the seeder be refactored** so that `seed()` accepts a `manual_stocks` parameter instead of a separate module? Or keep `reseed.py` as the orchestrator?

4. **Existing `ticker_groups` vs `duckdb_ticker_groups`** — should we merge them? i.e., just add a `product_id_override` field to entries in `ticker_groups`? Or keep separate groups for clarity?

5. **What about the 7 cash/treasury instruments** (`us5yt-rr` through `eur-usd`)? These tickers are already in `demo-market-1Jun26` but have no `product_type` the seeder recognises (yield = not a fund/stock). Do we need a new `product_type` like `treasury_yield` or can the bridge handle them as `bond`/`money_market_fund`?
